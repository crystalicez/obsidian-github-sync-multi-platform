# Official Local Qualification and Release Design

## Goal

Add a first-class maintainer workflow that can qualify and publish a stable release entirely from a trusted local machine without GitHub Actions while preserving the repository's exact-SHA safety model.

The local path must not be a bypass. It must:

1. qualify the exact commit that will be released,
2. persist auditable qualification evidence on GitHub,
3. fail closed if `master`, metadata, qualification evidence, toolchain state, or publication state changes,
4. retain deterministic/package gates in addition to the real GitHub E2E,
5. prevent destructive local E2E from targeting the source repository or a shared/static branch,
6. avoid blind retries after ambiguous Git/GitHub mutations,
7. never auto-delete, force-update, or clobber partial stable publication state,
8. verify the bytes of every release asset before and after publication,
9. remain usable from PowerShell/Windows as well as macOS/Linux,
10. coexist with the current GitHub Actions qualification/release path rather than deleting it.

The current V4 sync/runtime behavior and live-E2E scenario semantics are unchanged by this work. Safety checks around invoking the live suite may be strengthened.

## Current State and Constraints

- `pnpm test:github-e2e:quick` runs the credentialed real-GitHub suite locally and loads `.env.github-e2e` automatically when shell variables are absent.
- The local GitHub E2E runner currently rejects protected-looking branch names but does not itself reject `GITHUB_E2E_OWNER/GITHUB_E2E_REPO` when they identify this source repository.
- `.github/workflows/github-e2e-live.yml` is stricter: it rejects a target E2E repository equal to the source repository and uses a run-specific disposable branch.
- The deterministic release gates already exist as pnpm scripts: build, fast/repeat/recovery/resource/feasibility tests, E2E compile, and package validation.
- `scripts/validate-package.mjs` requires `main.js` to exist and be non-empty. `main.js` is ignored and is generated by `pnpm build`, so package validation cannot run before build on a fresh checkout.
- `.github/workflows/release.yml` currently requires a successful exact-SHA `github-e2e-live.yml` Actions run before creating a stable release.
- The current Actions stable workflow rechecks that the target SHA is still current `master` immediately before publication and creates a stable release for the exact SHA.
- The current release ZIP uses the GitHub repository name `obsidian-github-sync-multi-platform` as its top-level directory and ZIP filename prefix. This differs from `package.json.name` and `manifest.id`, which are `encrypted-github-sync-multi-platform`.
- GitHub CLI's `gh release create <tag> <assets...>` implementation creates a temporary draft when assets are supplied to a non-draft release, uploads the assets, publishes the release, and attempts to delete that draft if upload or publication fails. Therefore the local safety invariant "never auto-delete partial publication state" cannot be implemented with a one-shot non-draft `gh release create ...assets...` command.
- The repository currently has no `.gitattributes`, so Windows checkout line-ending policy can change bytes of tracked text release assets even while Git reports the tree as clean.
- Node is pinned by `.node-version`; pnpm is pinned by `package.json#packageManager`. Official local qualification must enforce those versions rather than merely record them.

## Chosen Architecture

Use two separate durable Git namespaces and an explicit publication state machine:

1. **Qualification evidence:** a namespaced annotated Git tag containing a validated JSON receipt and pointing directly to the qualified commit.
2. **Stable publication claim:** the normal lightweight stable `x.y.z` tag, created explicitly and without force at the qualified SHA.
3. **Release staging:** an explicit GitHub **draft** release associated with that already-created stable tag.
4. **Artifact verification:** verify the exact four release assets before the draft can be published.
5. **Final publication:** revalidate remote `master`, the exact qualification tag object, stable tag, metadata, and draft assets, then publish the draft explicitly.
6. **Post-publication verification:** re-read stable tag and release state and prove that the final release is exact and complete.

New public maintainer commands:

```text
pnpm qualify:local
pnpm release:local -- <x.y.z>
```

The qualification command performs all required gates and creates/pushes a qualification receipt only after success. The release command trusts that exact-SHA receipt for expensive qualification work, reruns inexpensive publication-machine gates, packages deterministic assets, claims the stable tag, stages a draft, verifies asset bytes, and publishes explicitly.

GitHub Actions remains an independent release path. The local flow does not weaken or modify the existing Actions qualification authority in `.github/workflows/release.yml`.

## 1. Trust and Invariants

### 1.1 Authority

A local qualification tag is a **maintainer attestation**, not cryptographic proof that the tests physically ran. Anyone able to forge the qualification tag already has source tag-push authority; anyone able to publish the stable release also has release/write authority.

Version 1 does not require GPG or SSH signing. Signing may be added later as defense in depth without changing the exact-SHA model.

### 1.2 Exact-SHA rule

Qualification is valid for exactly one full commit object ID. For this repository's current SHA-1 object format that is a lowercase 40-hex SHA.

If `master` advances, the old receipt remains historical evidence but cannot qualify the new tip. Version equality, tree similarity, or prior runtime evidence never substitutes for exact commit identity.

The source tree, lockfile, release scripts, toolchain declarations, and release metadata are transitively bound by that commit.

### 1.3 Remote state is authoritative

Local tracking branches and local tag refs are never release authority.

- Remote `master` must be queried directly.
- Qualification verification must begin from the remote qualification ref/object, not from a same-named local tag.
- Stable-tag existence/target must be queried from the remote.
- Release/draft existence must be determined from GitHub state.

A fetch may populate the local object database or `FETCH_HEAD`, but verification must remain anchored to the remote ref object ID that was observed.

### 1.4 Qualification object identity is part of the invariant

It is not sufficient for a qualification ref merely to peel to the same commit.

When `release:local` first validates the qualification tag it snapshots the **remote annotated tag object SHA**. Every final race check must require that the remote qualification ref still points to that same tag object SHA. A delete/recreate or replacement receipt that still peels to the same commit is a change and must abort publication.

The annotated qualification tag object itself must point directly to a `commit`, not to another `tag` object.

### 1.5 No secret persistence or unsafe diagnostics

The qualification receipt must never include `GITHUB_E2E_TOKEN`, GitHub CLI credentials, `.env.github-e2e` contents, or remote URLs containing embedded userinfo/tokens.

Diagnostics may print normalized `owner/repo`, ref names, SHAs, branch names, and copy-paste inspection commands, but any remote URL shown to the user must be sanitized.

### 1.6 Fail-closed lookup semantics

For every remote lookup, distinguish **proven absent** from **unknown/error**.

- A proven missing ref or HTTP `404` may mean absent.
- Authentication errors, rate limits, `5xx`, malformed responses, command crashes, timeouts, and network failures are not absence and must abort.
- A nonzero `gh`/`git` exit code must never automatically be translated to "not found".

### 1.7 Stable version format

Stable versions are canonical numeric triples only:

```text
0.0.0
1.0.8
12.34.567
```

Each component is either `0` or a non-zero digit followed by digits. Leading-zero forms such as `01.0.8` are invalid. Comparison must be numeric without relying on JavaScript `Number` precision; use `BigInt` or equivalent exact component comparison.

Qualification tags are outside this exact `x.y.z` namespace and must never participate in stable-version ordering.

## 2. Qualification Receipt

### 2.1 Tag namespace

For stable version `1.0.8` and commit SHA `<sha>`, the authoritative tag name is:

```text
qualification/local/v1/1.0.8/<sha>
```

The full SHA is deliberately included in the ref name. Qualification tags are never force-updated or reused for another tag object.

### 2.2 Annotated-tag message

The annotated tag message is UTF-8 JSON with this v1 schema:

```json
{
  "schemaVersion": 1,
  "kind": "obsidian-sync-local-qualification",
  "repository": "crystalicez/obsidian-github-sync-multi-platform",
  "commitSha": "<40-hex-sha>",
  "version": "1.0.8",
  "result": "success",
  "qualifiedAt": "2026-08-26T00:00:00.000Z",
  "durationMs": 123456,
  "platform": "win32-x64",
  "nodeVersion": "v22.11.0",
  "pnpmVersion": "9.12.3",
  "e2eSuite": "github-e2e-quick",
  "gates": [
    "metadata-validation",
    "install-frozen",
    "build",
    "package-validation",
    "fast-tests",
    "repeat-tests",
    "recovery-tests",
    "resource-tests",
    "feasibility-tests",
    "github-e2e-compile",
    "github-e2e-live",
    "github-e2e-cleanup-verified"
  ]
}
```

For schema v1, authority validation requires:

- exact `schemaVersion`, `kind`, `repository`, `commitSha`, `version`, `result`, and `e2eSuite`,
- `nodeVersion` exactly matching the committed `.node-version`,
- `pnpmVersion` exactly matching the version declared by the committed `packageManager` field,
- the exact ordered `gates` array above, with no duplicates, omissions, or extra gates.

`qualifiedAt`, `durationMs`, and `platform` are audit metadata. They must be syntactically valid but do not determine release eligibility beyond receipt validity.

### 2.3 No local qualification-ref residue

Prefer creating the annotated tag **object** without first creating a persistent local `refs/tags/...` ref. The implementation may use `git mktag` (with an injected command runner in tests) to create the tag object, then push that object SHA to the exact remote qualification ref.

This avoids stale local qualification tags becoming accidental authority and avoids cleanup questions after an ambiguous push.

If implementation instead uses a temporary local ref, that ref must be namespaced as temporary, must never be used as authority, and must not be confused with the final remote ref.

### 2.4 Idempotency

At the beginning of qualification, query the exact remote qualification ref.

If it already exists and all of the following are proven:

- the remote ref points to an annotated tag object,
- that tag object points directly to the expected commit SHA,
- its tag name matches the expected qualification ref name,
- the receipt validates against the current schema/version/repository/toolchain/gate contract,

then `qualify:local` may report the SHA as already qualified and exit successfully without rerunning the expensive gates.

Any mismatch fails closed. An existing qualification ref is never replaced.

## 3. `pnpm qualify:local`

Implement `scripts/local-qualify.mjs` with shared validation/orchestration helpers in `scripts/local-release-lib.mjs`.

### 3.1 Preflight

Before expensive work:

1. require a clean Git working tree, including non-ignored untracked files,
2. require current branch `master`,
3. resolve `HEAD` and require the expected full commit SHA form,
4. normalize `origin` and require it to identify exactly `crystalicez/obsidian-github-sync-multi-platform`, supporting canonical HTTPS and SSH forms,
5. query remote `refs/heads/master` directly and require it to equal `HEAD`,
6. validate package/manifest/versions metadata without requiring generated `main.js`,
7. require `process.version` to match `.node-version` exactly,
8. require Corepack pnpm to resolve to the version declared in `package.json#packageManager`,
9. require a usable Git tagger/committer identity before running long gates,
10. prove the exact remote qualification ref is absent or already-valid according to section 2.4,
11. require the real-E2E owner/repo/token configuration to be resolvable from process environment or `.env.github-e2e`, without printing credential values,
12. reject an E2E target repository equal to the source repository before any destructive test mutation.

Do not trust a possibly stale local `origin/master` ref.

### 3.2 Harden the local E2E safety boundary

The official qualification path must not rely only on the existing branch-name blacklist.

Strengthen `scripts/run-github-e2e.mjs` or a shared E2E preflight helper so every destructive local run also:

- normalizes the source repository from the current Git `origin`,
- rejects `GITHUB_E2E_OWNER/GITHUB_E2E_REPO` when it equals the source repository,
- retains the existing protected-looking branch blacklist,
- retains the real tests' default-branch rejection,
- validates that the E2E repository can be read before mutation.

For `qualify:local`, do **not** use the static branch name from `.env.github-e2e` as the official run branch. Generate a unique child-process override such as:

```text
obsidian-sync-e2e/local-<sha12>-<random-id>
```

Only the child process environment is overridden; `.env.github-e2e` is not rewritten.

The unique branch name must be printed so residue can be inspected after a hard cancellation.

### 3.3 Gate order

Run gates sequentially and stop on first failure:

```text
# metadata-validation is the pure preflight check above
corepack pnpm install --frozen-lockfile
corepack pnpm build
corepack pnpm validate:package
corepack pnpm test
corepack pnpm test:repeat
corepack pnpm test:recovery
corepack pnpm test:resource
corepack pnpm test:feasibility
corepack pnpm test:github-e2e:compile
# GITHUB_E2E_BRANCH is overridden with the unique qualification branch
corepack pnpm test:github-e2e:quick
# explicit read-only verification that the unique E2E branch is absent
```

The ordering is intentional:

- pure metadata/toolchain checks reject cheap failures before installation,
- build precedes `validate:package` because package validation requires generated `main.js`,
- the live E2E remains last because it is the slowest and most destructive gate,
- qualification is not complete until the unique disposable E2E branch is proven absent after the suite succeeds.

A hard cancellation may leave branch residue, but no qualification receipt can be created because the qualifier process did not reach receipt publication.

### 3.4 Post-gate revalidation

Immediately after all gates and cleanup verification pass, before creating a receipt:

- require the working tree still clean apart from ignored generated/test outputs,
- require `HEAD` is unchanged,
- query remote `master` again and require it still equals the qualified SHA,
- re-read and fully validate package/manifest/versions metadata,
- recheck the required Node/pnpm toolchain declarations and running versions,
- recheck that the exact qualification ref has not appeared concurrently.

If `master` advances or any invariant changes, do not create a qualification tag. The maintainer must update and rerun qualification for the new exact SHA.

### 3.5 Qualification tag object creation and push

Create one annotated tag object whose message is the canonical receipt JSON and whose target is the exact commit.

Push only that object to:

```text
refs/tags/qualification/local/v1/<version>/<sha>
```

without force.

On push result:

- **success:** query the remote ref again and prove its tag object SHA exactly equals the locally created tag object SHA and directly targets the expected commit;
- **explicit remote rejection because the ref now exists:** inspect the existing remote receipt; succeed only if it is independently valid according to section 2.4, otherwise fail;
- **transport/unknown outcome:** do not blindly retry. Query remote state. Succeed only if the remote ref object SHA is exactly the tag object SHA created by this invocation and its receipt validates; absent or mismatched state fails closed with inspection commands.

## 4. `pnpm release:local -- <version>`

Implement `scripts/local-release.mjs`. This command publishes a stable GitHub Release without invoking GitHub Actions.

### 4.1 Release preflight

Require:

1. one explicit canonical stable `x.y.z` argument,
2. clean Git working tree,
3. branch `master`,
4. canonical `origin`,
5. exact `HEAD == remote master`,
6. `package.json.version == manifest.json.version == requested version`,
7. `versions.json[version] == manifest.minAppVersion`,
8. running Node and Corepack pnpm versions match the committed toolchain declarations,
9. requested version is greater than every other remote stable `x.y.z` tag,
10. no existing remote stable tag for the requested version,
11. no published or draft GitHub Release for the requested version,
12. GitHub CLI is installed and authenticated for the canonical repository,
13. the exact qualification ref exists remotely for `(version, HEAD)` and validates.

Stable-tag enumeration must read all relevant remote refs rather than a limited first page/list. Qualification tags must be filtered out by the exact stable-version parser.

For v1, a stable tag or draft/published release already present **before this invocation** is treated as partial/concurrent publication state, not as an automatic resume opportunity. Fail closed and print inspection instructions. This prevents two maintainers/processes from both deciding that the same partially-created state is theirs.

A future explicit recovery/resume command may be designed separately; it is not implicit in `release:local` v1.

### 4.2 Remote-only qualification verification

Starting from the remote qualification ref, validate and snapshot:

- remote ref object type is `tag`, not `commit`,
- remote annotated tag object SHA = `qualificationTagObjectSha`,
- tag object's declared tag name equals the expected qualification tag name,
- tag object's target type is exactly `commit`,
- direct target commit equals `HEAD`,
- receipt schema/kind/repository/version/SHA/result/toolchain/gates match section 2,
- `e2eSuite == github-e2e-quick`.

Do not accept an annotated-tag-to-annotated-tag chain even if the final peel reaches `HEAD`.

Do not allow a local same-named tag to override or substitute for the observed remote object.

### 4.3 Pre-publication rerun

The release command does **not** rerun the real-GitHub E2E, repeat loop, recovery/resource/feasibility suites because the exact-SHA qualification receipt is authority for those expensive gates.

It reruns publication-machine integrity gates:

```text
corepack pnpm install --frozen-lockfile
corepack pnpm build
corepack pnpm validate:package
corepack pnpm test
corepack pnpm test:github-e2e:compile
```

Then re-read metadata and recheck the working tree, `HEAD`, and remote `master` before packaging.

### 4.4 Final pre-mutation race check

Immediately before creating any stable publication state:

- require working tree still clean apart from ignored generated/test/package outputs,
- require `HEAD` unchanged,
- query remote `master` and require the exact same SHA,
- require the remote qualification ref still points to the exact snapshotted `qualificationTagObjectSha`,
- require that tag object still validates and directly targets `HEAD`,
- require requested stable tag still absent,
- require requested draft/published release still absent,
- re-read release metadata and require it still matches the requested version.

Any change aborts before stable publication mutation.

## 5. Plugin Packaging and Cross-Platform Bytes

### 5.1 Exact release asset contract

Preserve the existing repository-name-based release contract exactly.

For version `1.0.8`, the ZIP filename is:

```text
obsidian-github-sync-multi-platform-v1.0.8.zip
```

It contains exactly:

```text
obsidian-github-sync-multi-platform/main.js
obsidian-github-sync-multi-platform/manifest.json
obsidian-github-sync-multi-platform/styles.css
```

The release uploads exactly four assets:

```text
main.js
manifest.json
styles.css
obsidian-github-sync-multi-platform-v<version>.zip
```

Do not derive the ZIP/root name from `package.json.name` or `manifest.id`.

### 5.2 ZIP implementation

Add `scripts/package-plugin.mjs`.

Node 22 does not provide a built-in ZIP writer. Do not implement a custom ZIP/CRC32 format writer solely to avoid a development dependency.

Use one small pure-JavaScript ZIP dependency for release tooling. The chosen v1 dependency is `fflate` (currently `0.8.3` upstream at design time), added as a development dependency and locked by `pnpm-lock.yaml`. The implementation plan must pin/review the actual version being committed rather than silently floating it.

The packager must:

- read the three source asset files as raw bytes,
- use POSIX `/` separators for ZIP entry names on every OS,
- emit entries in the exact order above,
- normalize timestamps/metadata so repeated packaging from identical input bytes is deterministic,
- never traverse or archive arbitrary workspace paths,
- write only beneath `.tmp/release/<version>/`, which is already ignored,
- overwrite only its known output path after validating the version/output target.

Compression algorithm/level is not an authority boundary, but the implementation should use a fixed setting to make byte-for-byte repeatability practical.

### 5.3 Line-ending determinism

Add a targeted `.gitattributes` policy for tracked text files that are uploaded directly as release assets:

```gitattributes
/manifest.json text eol=lf
/styles.css text eol=lf
```

`main.js` is generated by the build and must be deterministic under the pinned toolchain.

Avoid a broad repository-wide line-ending rewrite as part of this feature.

### 5.4 Local artifact manifest

Before the first stable publication mutation, compute and retain in memory a local artifact manifest for all four assets containing:

- exact asset name,
- byte size,
- SHA-256 digest.

This manifest is the comparison authority for draft and final release verification. It is not a persistent release authority and does not need to be committed or uploaded separately.

## 6. Stable Publication State Machine

### 6.1 Why publication is multi-step

Do not use a one-shot non-draft:

```text
gh release create <version> ...assets...
```

because GitHub CLI may create a temporary draft and automatically delete it when asset upload/publication fails. That behavior violates this design's no-auto-delete invariant.

Instead use an explicit state machine whose intermediate state is intentionally durable and inspectable.

### 6.2 State A: claim the stable tag

Create the stable `x.y.z` ref explicitly as a lightweight tag pointing to the exact qualified `HEAD`, preserving the repository's existing stable-tag type.

Prefer a direct no-force push such as the semantic equivalent of:

```text
git push origin <exact-sha>:refs/tags/<version>
```

Do not force and do not rewrite an existing stable tag.

Result handling:

- **push succeeds:** immediately query the remote stable ref and require it equals the exact qualified commit;
- **explicit rejection because the tag already exists:** another/previous publication owns state; abort even if the existing tag happens to point to the same commit;
- **transport/unknown outcome:** inspect remote state but do not continue publication automatically. If the tag is absent or mismatched, fail. If it exists at the exact SHA, report the state as ambiguous/partial and stop with inspection instructions.

The conservative unknown-outcome rule is intentional: unlike the annotated qualification object, a lightweight stable tag contains no per-invocation object identity that can prove which concurrent process created it.

### 6.3 State B: create an explicit draft and upload assets

Only after the stable tag is proven exact may the command create the GitHub release.

Use an explicit draft operation equivalent to:

```text
gh release create <version> \
  --repo crystalicez/obsidian-github-sync-multi-platform \
  --verify-tag \
  --draft \
  --title <version> \
  --generate-notes \
  [--notes-start-tag <previous-stable-x.y.z>] \
  main.js manifest.json styles.css <plugin-zip>
```

The actual Node process runner must pass argv elements directly and must not depend on POSIX shell continuation syntax.

If a lower stable tag exists, explicitly pass the highest lower stable `x.y.z` tag as the generated-notes start tag so qualification tags can never accidentally affect release-note range selection. Omit the option for the first stable tag.

Because `--draft` is explicit, the draft is intentional durable state; the local script must never delete it automatically after an error.

If draft creation/asset upload returns an error or unknown outcome, inspect remote release state and report it. Do not retry, clobber, upload over an existing same-name asset, or delete anything automatically.

### 6.4 State C: verify the draft and assets

Before publication, prove:

- stable tag still points to exact qualified SHA,
- exactly one relevant draft release exists for the requested tag,
- release tag is exactly the requested version,
- `draft == true`,
- `prerelease == false`,
- the set of assets is exactly the expected four names, with no extras,
- every asset reports completed/uploaded state,
- every asset byte size equals the local artifact manifest,
- every asset SHA-256 digest equals the local artifact manifest.

If GitHub exposes a trustworthy SHA-256 asset digest, use it. If the digest is absent for an otherwise uploaded asset, download that asset to a fresh ignored temporary directory and hash the downloaded bytes locally before accepting it.

Correct names alone are never sufficient reconciliation evidence.

### 6.5 State D: final evidence/race recheck

Immediately before publishing the verified draft, recheck all of the following:

- working tree/`HEAD` invariant,
- remote `master == HEAD`,
- remote qualification ref object SHA still equals the snapshotted `qualificationTagObjectSha`,
- qualification tag still directly targets `HEAD` and its receipt still validates,
- stable tag still equals `HEAD`,
- release metadata still matches the requested version,
- draft is still draft/non-prerelease,
- exact four remote assets still match the local artifact manifest.

Any mismatch aborts while leaving the draft/tag untouched for inspection.

### 6.6 State E: publish the draft explicitly

Publish only after State D passes, using the semantic equivalent of:

```text
gh release edit <version> \
  --repo crystalicez/obsidian-github-sync-multi-platform \
  --draft=false
```

Do not use `--clobber` or any command that deletes/replaces existing assets.

If publication returns failure/unknown outcome, do not blindly retry. Inspect GitHub state:

- if an exact non-draft, non-prerelease release now exists for the requested stable tag and all four assets still match the local artifact manifest, reconcile as success;
- if it remains a draft, is missing, is partial, contains wrong assets, or any lookup is unknown, fail closed and print inspection commands;
- never auto-delete the draft or stable tag.

### 6.7 State F: post-publication verification

Even after a successful publish command, re-read remote state and require:

- stable tag equals the exact qualified SHA,
- qualification ref still points to the same snapshotted tag object SHA,
- release is non-draft and non-prerelease,
- release tag is the requested version,
- exact asset set equals the expected four names,
- all sizes and SHA-256 digests match the local artifact manifest.

Only then print the final release as successful.

### 6.8 Partial state from a previous invocation

Version 1 intentionally does not auto-resume a stable tag or draft created by a previous invocation.

On a later `release:local` invocation, any pre-existing requested stable tag or draft/published release causes preflight to stop and print read-only inspection commands. This avoids incorrectly treating concurrent or manually-created state as owned by the current process.

Manual remediation/completion is a maintainer decision. The tool never automatically deletes a tag/release merely because a prior run failed.

## 7. GitHub Actions Coexistence

Keep `.github/workflows/github-e2e-live.yml` and `.github/workflows/release.yml` intact as an independent qualification/publication mechanism.

The Actions stable-release workflow continues to require Actions-native exact-SHA qualification. It does not automatically trust local qualification tags in v1.

The official documentation presents two independent paths:

- **Local maintainer path:** `qualify:local` -> annotated qualification tag -> `release:local` state machine.
- **GitHub Actions path:** GitHub E2E Live -> Stable Release workflow.

Both retain exact-SHA semantics. Neither path can qualify another commit merely because the version matches.

The local implementation must not modify Actions workflows merely to share authority. Shared pure helpers may be introduced only where they do not change Actions behavior.

## 8. Test Strategy

Use TDD for release machinery. Tests must not create real source-repository tags/releases or mutate a real release repository.

All process-heavy release tests should live under `tests/feasibility/` (for example `tests/feasibility/local-release-*.test.mjs`) because the current test classifier has no `release` tier. Do not create `tests/release/` and assume it is isolated; that path would currently classify as the ordinary fast tier.

### 8.1 Pure/shared validation tests

Test `local-release-lib.mjs` with injected command/GitHub runners for:

- canonical stable-version parsing, leading-zero rejection, and large-component exact comparison,
- canonical repository normalization for HTTPS, scp-style SSH, and `ssh://` origin forms,
- rejection/redaction of credential-bearing or non-canonical remotes,
- qualification tag naming,
- canonical receipt generation/parsing/validation,
- wrong schema/kind/repository/SHA/version/result/toolchain/gate order rejection,
- duplicate/missing/extra gate rejection,
- lightweight qualification-tag rejection,
- nested annotated-tag rejection,
- remote tag-object SHA and direct-commit mismatch rejection,
- remote-master mismatch rejection,
- dirty-tree/non-master rejection,
- remote lookup classification: absent vs auth/rate-limit/5xx/network/timeout/malformed response,
- stable-tag filtering that ignores qualification tags.

### 8.2 Qualification orchestration tests

With fake runners plus temporary local Git fixtures where useful, prove:

- metadata validation happens before install,
- build happens before `validate:package`,
- a fresh checkout without `main.js` reaches build rather than failing package validation early,
- stale ignored `main.js` cannot substitute for building current source,
- first failing gate stops the run,
- no qualification tag object/ref is published before all gates and cleanup verification pass,
- wrong Node/pnpm version fails before expensive tests,
- missing Git tagger identity fails before expensive tests,
- source-repository E2E target is rejected,
- official qualification overrides a static `.env` E2E branch with a unique run branch,
- two generated qualification branch names do not collide,
- successful live E2E is not sufficient until branch absence is verified,
- remote `master` is rechecked after the long run,
- changed remote `master` prevents qualification,
- successful run creates exactly one annotated tag object directly targeting the commit,
- no same-named local qualification tag is required as authority,
- push error + exact same remote tag-object SHA reconciles as success,
- push error + absent/mismatched remote object fails without blind retry.

### 8.3 Release orchestration tests

Prove:

- unqualified SHA cannot release,
- receipt for another version/SHA cannot release,
- replacing qualification receipt with a different tag object that peels to the same commit is detected by final race check,
- stale/malicious local qualification ref cannot override remote evidence,
- expensive live E2E/repeat/recovery/resource/feasibility gates are not rerun by `release:local`,
- publication-machine gates run before packaging,
- remote `master` is rechecked immediately before any stable mutation and immediately before draft publication,

## 10. Rollout Sequence

The runtime/E2E fix SHA `35e98cea924702293bde62d064a83d52eca6d898` is already the current `master` base and remains preserved by the fix branch history. Treat that merge/base step as complete rather than instructing the maintainer to merge it again.

The local-qualification implementation continues on a separate branch based on that master state.

Before the first real local release:

1. implement and review the local qualification/release tooling,
2. merge the implementation to `master`,
3. require ordinary deterministic CI to pass on the final `master` SHA,
4. run `pnpm qualify:local` on that exact final `master` SHA,
5. independently inspect the remote annotated qualification ref and exact tag-object/commit binding,
6. run `pnpm release:local -- <version>`,
7. verify the final stable tag and four release assets after publication.

Because release-tooling changes alter the commit SHA, earlier live-E2E evidence for `35e98cea...` cannot qualify the final release commit. `pnpm qualify:local` must run once on final `master`; that command includes the full real-GitHub E2E and cleanup verification.

## Non-goals

- No removal of GitHub Actions workflows.
- No automatic release on push/version bump.
- No lightweight qualification tags.
- No force-updating qualification or stable tags.
- No requirement for GPG/SSH tag signing in v1.
- No storage of E2E secrets in tags, files, artifacts, or logs.
- No relaxation of the exact-SHA or exact-qualification-tag-object rules.
- No automatic deletion/clobber of partial stable publication state.
- No implicit cross-invocation resume of a pre-existing stable tag or draft in v1.
- No custom hand-written ZIP container implementation when a small audited pure-JS development dependency suffices.
- No broad repository-wide line-ending rewrite.
- No V4 sync/runtime behavior changes.
- No dependency on a local JSON receipt as release authority.

## Acceptance Criteria

The work is complete when:

1. `pnpm qualify:local` runs from PowerShell and POSIX shells without shell-specific environment-assignment syntax,
2. qualification cannot create a receipt unless metadata, pinned toolchain, every required gate, real GitHub E2E, E2E cleanup verification, and post-gate remote-master checks succeed,
3. official local E2E cannot target this source repository and uses a unique run-specific branch,
4. a fresh checkout with no ignored `main.js` can qualify because build precedes package-artifact validation,
5. the pushed annotated qualification tag is remotely verifiable as one exact tag object directly bound to the exact version/SHA and required receipt schema,
6. `release:local` snapshots qualification tag-object identity and detects replacement even when the replacement peels to the same commit,
7. `release:local` refuses dirty, non-master, stale-master, wrong-toolchain, unqualified, mismatched-version, duplicate, non-monotonic, pre-existing-partial, or unknown remote-state publication attempts,
8. stable publication claims the exact stable tag without force before draft creation,
9. local publication never uses the GitHub CLI one-shot non-draft asset path that can auto-delete temporary release state,
10. draft assets are exactly the expected four names and their byte sizes/SHA-256 digests match the local artifact manifest before publication,
11. remote `master`, qualification tag-object identity, stable tag, metadata, and asset bytes are rechecked immediately before explicit draft publication,
12. ambiguous stable-tag/draft/publish outcomes are inspected rather than blindly retried, auto-deleted, or clobbered,
13. the final published release is post-verified as non-draft/non-prerelease at the exact stable tag/SHA with byte-matching assets,
14. ZIP naming/root layout exactly preserves the current repository-name-based contract and is deterministic across supported OSes under the pinned toolchain,
15. process-heavy release tests live in the existing feasibility tier and cover the real Git-object semantics that mocks could hide,
16. the existing Actions release path remains functional and unchanged in authority,
17. maintainer documentation clearly identifies the local path as an official supported release flow and explains partial-state inspection/recovery boundaries.
