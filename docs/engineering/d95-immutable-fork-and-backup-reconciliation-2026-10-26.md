# D95 — Immutable source-fork reads and read-only ambiguous backup creation recovery

> **Implementation overview.** See [D95 detailed source-snapshot and recovery contract](d95-immutable-fork-snapshot-and-backup-ambiguity-2026-10-26.md) for the explicit policy boundary. Release gate remains blocked.

Date: 2026-10-26. Owner-approved baseline: D90 independent old-branch Sync, D91 mandatory **source + frozen backup + fresh orphan destination**, all in one GitHub physical repository. **This is NOT a release or an authorization to perform a live re-encryption.**

## What changed

### Immutable source-fork mode
- `verifyV4ReencryptionSourceObjects` retains legacy `require-stable-head` by default for callers that still need it, while explicitly permitting `sourceRefPolicy:"pinned-immutable-commit"` for the D90 fork source path. This latter mode still authenticates the complete V4 index, HMAC metadata, path identity, all file ciphertext, AES-GCM plaintext and SHA-256 hashes from one immutable pinned Git commit. It is not permission to ignore missing/corrupt blobs or mix objects from multiple commits.
- `verifyGitHubReencryptionForkSource` verifies physical GitHub repository identity before/after, observes the exact source branch once, pins its complete 40-hex SHA, and subsequently uses immutable commit/tree/blob APIs. It does not require an unrelated device to stop advancing **source HEAD** once the snapshot boundary is fixed.
- The 5-step Wizard **preview** uses the fork-aware read-only entrypoint, and double-checks GitHub numeric repository identity/default branch around verification. The Wizard remains incapable of creating a ref or changing settings.

### Frozen pointer and full encrypted content
- The earlier D89 `inspectV4SameRepositoryBackupRef` pointer-only report was repaired to check Source branch presence + exact scope, **not** require its current HEAD to equal the pinned SHA. A backup ref must still point exactly to the approved source snapshot SHA and both SHA-pinned immutable commit/tree/parents must match; wrong physical GitHub repo, unavailable refs, or moved backup ref fail closed. The renamed report no longer falsely asserts that both branch refs point to the same commit after old-branch development continues.
- D94 `verifyGitHubFrozenReencryptionBackup` reads via the **backup branch** (whose encrypted config intentionally still says `owner/repo#old-source-branch`) and verifies every authenticated file in the frozen snapshot. It checks scope, physical repository ID, pinned snapshot commit and root Git tree, full Git blob identity and decrypted content. `backupContentsReadbackVerified:true` means **remote frozen-branch content only**; it does NOT prove backup creation provenance, separate physical storage, an installed Obsidian restore, durable local recovery or permission to publish/cut over.

### Ambiguous create-ref recovery classification (NEW D95)
- `src/lib/v4/reencryption-backup-reconcile.ts`: `inspectV4FrozenBackupAfterAmbiguousCreate` is a **read-only** inspector for a known pinned backup plan following a lost/ambiguous GitHub create-ref response. The backup client is type-scoped to Git read methods and exposes no mutation API.
- Checks exact source/backup/destination roles, expected backup branch client, numeric physical GitHub repository identity before/after, actual default branch stable before/after and not backup/destination; observes frozen backup ref twice.
- Report outcomes: `ref-unobserved-at-two-checks` (not proof of absence forever), `ref-occupied-by-other-commit` (never overwrite), or `matching-backup-full-readback` (uses D94 **complete decrypt/hash/content verification**, then rechecks the backup ref). A mid-operation ref change or GitHub error raises an error and returns **no success report**. All outcomes freeze `automaticallyRetryCreateAuthorized:false`, `overwriteAuthorized:false`, `destinationPublicationAuthorized:false`, `cutoverAuthorized:false`, `creationProven:false`.
- The inspector is **not wired** to the existing Wizard, a release migration writer or ordinary Sync. Its status may guide a future deliberate recovery flow but does not itself authorize a new create or cutover.
- Double/triple Git ref samples are **not an atomic ref lock** and do not eliminate ABA between samples; process crashes and GitHub admin/other writers remain independent threats. End-to-end backup provenance, remote ref protections, commit publication and recovery integration are unfinished.

Future work: safe end-to-end source/backup orchestration, independently tested same-repo complete restore to isolated scratch, genuine orphan destination transcode+commit/publish+full post-write verification, durable Node.js-only Windows WAL and crash-safe initiating-device-only switch. No GitHub Actions and no files over the owner's 100MB physical test-file limit.

## Limitations / release-honesty
All reports operate on observable GitHub data and caller-approved source snapshot metadata. The first public release still needs trusted end-to-end evidence: an independently verified snapshot boundary, original plaintext live-file parity, actual backup ref provenance and restoration, destination branch ciphertext full readback, interrupted migration recovery and installed Obsidian behavior. A branch snapshot is in the same repository and inherits its account/repository loss risk, explicitly accepted by the owner under D88.
