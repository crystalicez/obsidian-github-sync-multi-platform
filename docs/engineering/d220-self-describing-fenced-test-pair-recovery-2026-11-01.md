# D220 — Self-describing, non-authoritative encrypted Receipt/Selector evidence after Restart

Date: 2026-11-01. Scope: **internal read-only recovery path and test staging only**. The installed Re-encryption Wizard remains Preview-only. First-public-release gate remains **blocked**.

## The concrete D219 gap

D219 correctly stages D182 AES-GCM Receipt/Selector *test vectors* on a local adapter under one held migration lease, reads the ciphertext back, and uses D184 to diagnose partial writes. However D184 needed a caller-supplied **historical D183 contract** to derive its AAD and verify the encrypted pair. On a real process restart this historical JavaScript object can disappear, making the new test pair impossible to authenticate from persisted bytes alone. Treating a reconstructed or guessed contract as trusted would be unsafe.

D220 therefore persists a canonical, **untrusted, nonsecret** contract bootstrap record, `<indexRoot>-rekey-proposed-<runId>/contract.json`, **before** D219's encrypted `marker.json` Receipt and `selector.json`. Its fields are the exact D183 transaction ID, immutable three-branch migration identity, and six hashed provenance digests. The manifest stores **no passphrases, journal key, tokens, plaintext file paths or actual GitHub API writes**. It is at most 8 KiB, requires schema/phase/exact keys, canonical JSON and a valid D182 contract. The manifest is NOT an authentication, a persisted commit receipt or a Cutover authorization.

## Added implementation

- `reencryption-commit-pair-test-vectors.ts` exports its existing strict contract validator for use at the **untrusted file boundary**; the same validation rules now protect both the D182 ciphertext reader and the D220 JSON bootstrap.
- `reencryption-persisted-test-contract.ts` encodes/decodes canonical, strictly bounded bootstrap JSON. Reject missing/torn, oversized, foreign, extra-field or noncanonical encodings. The record is a hint until independent cryptographic verification succeeds.
- `reencryption-fenced-persisted-test-pair.ts` D219 writer now requires NO prior manifest, creates the proposal directory, writes/reads back `contract.json` first, then encrypted Receipt, then encrypted Selector. Checkpoint/WAL/fence/owner lease at each boundary, read back all three records, call D184, and reread manifest before returning. Partial output remains untouched on error and blocks automatic retry.
- `reencryption-fenced-persisted-test-pair-restart.ts` provides `inspectV4FencedPersistedTestPairAfterRestart(prepared)`: a **read-only** inspector requiring only the restarted D176 Prepared input, journal key and independently accessible local storage. No historical D183 contract parameter. Under **ONE external initiating-device holder** it authenticates WAL and byte-exact Sync Fence, reads the bounded manifest, validates its migration identity and consistency with current Source Settings/SecretStorage, calls D184 using a guarded **borrowed holder** to authenticate the actual persisted D182 AES-GCM Receipt/Selector and Source/Shadow/Prepared/Intent/WAL evidence, then independently reads the manifest again and performs one final readback after the second observation. A regression caught replacement immediately after a successful second read; the final readback now fails closed on that observed drift. Finite readbacks cannot prevent an external OS writer from mutating after the final read. A coherent test pair returns `historicalTestPairCryptographicallyLinked: true` but still `observation: manual-recovery-required` and five hardcoded false permissions; other cases return false. Never select Destination or resume Sync.

## Behavioral proof

The regression first showed a **genuine RED**: D219 success had no saved `contract.json` and failed the new assertion `restart-readable nonsecret contract must be persisted`. New tests then exercise contract readback without caller historical witness, reconstructing input/Settings/key after staging, preserved no-password manifest; corrupted/missing/foreign/extra-key/oversized/canonical-but-tampered contract and broken Receipt/Selector; WAL/Fence/Secret loss; changed manifest between read passes; a forged holder that never invokes the inspector; and interruption **after writing bootstrap manifest but before Receipt**. Every case keeps Sync blocked, preserves recorded evidence, and never authorizes Cutover, Git writes, rollback or old-key cleanup. The composed D183/D184 actual AES-GCM and current local evidence readers execute in tests.

All tests use deterministic in-memory adapter fixtures (including simulated interrupted storage), not genuine power loss or a production Obsidian platform runtime. A recreated input object is **not a restarted OS process**. D220 does not perform a fresh full Git remote content scan; its historical test-pair observation must not be mistaken for the stronger D217 remote Backup+Destination proof. These paths are for preparation/recovery diagnostics only.

## Still blocking release

D220 is not a production committed Receipt/Selector, transaction commit point, crash-durable filesystem proof or best-effort automatic Cutover. Restart-safe Source→Destination Branch/SecretStorage/active Index/Settings selection, qualification for Manual Recovery or Resume Sync, multi-device stale-client safety, safe migration user workflow and real installed Desktop/Android/iOS acceptance remain unimplemented. Keep 3 branches, Source old-key independent syncing, frozen Backup, orphan Destination, old passphrase and Git history. No Native Helper, GitHub Actions, credentialed GitHub mutation, real Vault writes, force push, release, merge or branch deletion.
