# Stage D96 — First genuine encrypted orphan-root Git writer, create-only ref primitive, D90-compatible backup restore

Date: 2026-10-26. Status: **incremental implementation and offline integration evidence — NOT production-qualified**.

## Binding product decisions

The owner approved D90–D91: Re-encryption is an independent Git branch **FORK**, not an in-place key rotation or a fleet-wide cutover. The physical GitHub repository contains three required roles: original encrypted source branch (continues normal Sync), pinned immutable old-key backup ref, and a brand-new encrypted destination branch whose root Git commit has **zero parents**. Other devices can stay on the source branch indefinitely or manually change branch/credentials to follow. Do not add mandatory migration markers, block old-branch Sync, auto-merge, auto-delete refs, or force devices to follow.

## Actual D96 Backend implementation

- `src/lib/v4/reencryption-orphan-publication.ts` introduces **real GitHub Git-API operations**, separated into two steps and **not connected to UI**:
  1. `prepareV4ReencryptionOrphanCommit` consumes an already-finalized D79 encrypted vault object receipt inventory, validated destination records/keyring/config, one D94 fully decrypted authenticated backup content report, pinned old source SHA and source tree SHA, and a caller-owned exclusive migration lease. It checks complete object receipt coverage, fresh destination config and source/backup/destination separation. It builds new encrypted V4 remote config/head/index shards (including canonical shard SHA-256 signatures), creates Git metadata blobs, creates a **root Git tree WITHOUT `base_tree`**, creates a **zero-parent commit**, and reads back the tree and commit. No destination branch ref is created in this phase, and no plaintext logical paths are included in Git commit messages or directory names. Results remain `refPublished:false`, `cutoverAuthorized:false`.
  2. `publishV4ReencryptionOrphanRef` verifies the candidate root commit/tree/zero-parent ancestry, destination ref absent twice, correct physical GitHub repo/default branch and exact branch-scoped client; requires a caller-provided **durable publication-intent barrier** and exclusive lease before calling `createGitRef` **once**. It never calls `updateGitRef`, never rebases onto the old source branch, never retries the high-level mutation on an unknown GitHub response; then observes the resulting exact ref twice and reports `destinationContentReadbackVerified:false`, `cutoverAuthorized:false`.
- This is **not** yet an integrated, crash-durable migration coordinator: callbacks are trust boundaries and a fake/no-op callback is NOT proof of WAL durability. This writer is currently unreferenced by Settings, the sync runtime, or a real vault release workflow. Immutable blob staging with its encrypted WAL exists separately in D79–D81; wiring metadata/tree/commit/ref intent, restart reconciliation and native file durability into a single transactional orchestrator is mandatory.
- An existing separate **read-only exact-published-commit auditor** `verifyV4ReencryptionDestinationExactCommit` authenticates all committed ciphertext, cryptographic metadata, repo config, path manifests, immutable Git object identities and decrypted logical-file SHA-256. D96 now has an integrated in-memory GitHub simulator test that uses the **real V4 crypto and Git tree/commit/ref abstraction** from candidate through publication to exact-commit independent decryption, including wrong-new-key rejection. The exact-commit report still does NOT grant cutover. This test is not a credentialed real GitHub transaction or installed Obsidian acceptance.

## D90 consistency / UX defenses

- `assertV4OrphanDestinationRefObservations` now requires the *initial* authenticated source observation equal the approved pinned source SHA, but **permits subsequent valid full-commit source HEAD advancement**. It continues to require two independently absent destination-ref samples and exact physical repository ID before/after. These samples are not an atomic lock or authorization token. Prior D74 test rejecting a legitimate source movement was obsolete under D90; updated D96 regression covers both allowed advancement and wrong initial anchor/malformed later ref.
- Wizard now **clones and freezes** the initial Settings object; the UI compares owner/repo/branch/token/encryption/passphrase against current live Settings on each gated action. This detects in-place edits as well as object replacement while the modal is open and refuses re-key source reads with a changed connection. Temporary passphrase is cleared on close; publication remains blocked.
- D84 backup snapshot readback and D85 isolated scratch restore gained an explicit opt-in `sourceRefPolicy:"pinned-immutable-commit"`. The default `require-stable-head` behavior remains for older callers. In fork mode only, later old-source commits do **not** invalidate a still-stable, SHA-pinned snapshot; checks for snapshot-ID stability, authenticated manifest, every plaintext SHA-256, scratch restore readback, cancellation and isolated scratch remain mandatory. This does NOT imply independently durable platform-specific restore nor waive D86 Windows directory fsync `EPERM`. Stale comments about global stale-client fencing/quiescence were updated.

## Release-blocking remaining integration

The first-public-release Wizard gate **must remain `blocked`**:
1. Trusted end-to-end snapshot + backup-ref creation with durable provenance, complete backup decrypted readback and actual independent isolated restore; all three branch roles confirmed.
2. Restartable durable WAL across **all** immutable object writes, metadata/tree/commit/ref publication and ambiguous network outcome (D96's external intent callback alone is not enough); Windows Node.js directory fsync `EPERM` is unresolved, no Native OS Helper approved.
3. Full orchestrator that coordinates source ciphertext reading from an immutable commit, staging/new-key material, three-branch backup, actual remote publish, independent destination exact-commit readback, recovery on restart and safe refusal of concurrent **local** edits on the initiating device. Leave other devices syncing original source.
4. Crash-safe **initiating-device only** branch/passphrase/local index switch without Force Pull/Push, optional manual followers and second-device real encrypted restore testing.
5. Real GitHub test repository E2E with strict cleanup, installed Obsidian Windows/macOS/Linux and mobile acceptance, limits of 100 MB per physical test file, rate-limit/cancel/crash/retry/UX screenshots, and release security review. No GitHub Actions. No silent relaxation of any prior owner decisions.

The new code is real, executable Git-object creation code, but the user-facing button still deliberately says **Preview wizard** and cannot perform re-encryption yet. This is necessary to protect user vaults while the remaining recovery path is being qualified.
