## Implemented checks

- `scripts/native-installed-wal-writer-probe.ts` adds `verifySyntheticInstalledSourceParity(reader, noteText)`. It computes the actual UTF-8 SHA-256, makes one pinned synthetic Source record, calls the **production** two-pass local parity verifier through the real installed Runtime reader, and requires one verified file, the exact byte total, no unexpected files/open editors, and `initiatorLocalCutoverAuthorized:false`.
- `scripts/run-obsidian-disposable-wal-authoring.mjs --source-parity-and-revoke` arms the existing persisted Sync Fence on an installed Obsidian Runtime, creates its **live installed initiating reader** using the same revocable lease as the WAL writer, proves synthetic physical Source parity **before** beginning the encrypted WAL, then writes the one pending Backup intent to WAL generation 2. Revoking that very same lease must reject another real physical parity scan **with the exact lease-specific rejection** as well as a valid WAL slot overwrite and a WAL checkpoint. The independent Vault adapter observes both physical WAL slots and directory entries unchanged. The next installed Obsidian process reopens the WAL to authenticate the same pending Backup intent and enforces Manual Recovery; no Resume Sync or Cutover.
- `--source-parity-tamper` uses the same initially successful parity and authored pending WAL. While that WAL writer is still open, the test changes **only** the known synthetic Vault note by replacing ASCII `D377` with `E377` (same UTF-8 byte size). The production two-pass local parity scan must reject the actual modified disk content **specifically with its SHA-256 mismatch error**, not due to an invalid path/length or revoked lease. In a `finally` block the test restores the isolated note, checks both WAL slot hashes unchanged, closes the original WAL owner, restarts Obsidian and independently authenticates the pending WAL with Fence/Settings still blocked. This does not mean that a real OS write fence prevents concurrent edits: the test intentionally demonstrates detection of a write that an outside actor can still make.
- Existing default, `--kill-writer`, and D389 `--revoke-lease-after-intent` modes remain available. All modes keep the original test-only safe-directory checks, renderer Vault identity checks, sanitized exception logging, physical lock checks and automatic removal of their owned temporary Vault/Profile after termination.
