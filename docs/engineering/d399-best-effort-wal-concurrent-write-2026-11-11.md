# D399: reject a completed concurrent WAL write during Desktop best-effort readback

Date: 2026-11-11. Worktree `.worktrees/d87-owner-rekey-policy` only. Release gate remains **blocked**.

## Defect and risk

`acquireV4DesktopRekeyWalStorage()` exposes `assertBestEffortCheckpoint()` for the Windows installed migration when Node cannot prove directory fsync durability. The checkpoint independently reads each existing encrypted WAL slot twice and rejects residue, corrupt slot metadata and an active slot writer. Before D399, it tested the mutable `writing` flag only near the beginning and end. A second authorized adapter writer could **start, complete a slot rename, and finish** during a paused checkpoint. With `writing === false` again, two stable subsequent reads allowed the old checkpoint to report `best-effort-readback-only`, despite an interleaved WAL mutation.

The returned marker did not assert power-loss durability or authorize Cutover by itself. However, checkpoint callers need it to be a proof of a **settled, unmoving WAL readback interval**. A completed intervening write made that property false. The Mobile writer already separately prevents writes while `activeReaders > 0` in its cooperative adapter reservation; this repair targets the weaker Desktop overlap check.
