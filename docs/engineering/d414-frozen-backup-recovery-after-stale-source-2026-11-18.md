# Stage D414 — Installed Recovery must authenticate frozen Backup after stale Source advances

Date: 2026-11-18 (Asia/Bangkok). Existing production behavior, not a feature toggle. Scope: the same audit worktree and preapproved disposable GitHub repository as D412–D413.

## User-visible reason

Once a Source → frozen verified Backup → new-key orphan Destination migration rehearsal is prepared, an older device can remain pointed at Source and publish new old-key commits. The initiating device must still be able to **read-only authenticate the exact frozen Backup and Destination after restart**, even though the current Source HEAD has moved. It must *not* automatically merge cross-branch edits, resume Sync, perform local Cutover or delete the old passphrase. Wrong/changed Backup must still be rejected.

D413's installed two-Obsidian test confirmed an old-key peer really advanced Source while Backup/Destination remained unchanged, but it checked only that the initiating device was still fenced after restart. It did not call the full installed pre-cutover Recovery verifier *after* Source moved.

## Actual RED evidence

It builds an authenticated Source → Backup → new-key Destination using installed V4 runtime with encrypted WAL, advances the old Source ref independently to a valid descendant, restarts the runtime, then calls installed `inspectFencedReencryptionPreCutoverRecovery()` with original pinned SHA, tree, WAL generation and repository identity. On original code the result was `manual-recovery-required` rather than authenticated still-fenced, process `bd8e0be1-82fd-4858-8ec7-b24e40a30ce3` EXIT 1. ## Root cause

`src/lib/v4/reencryption-installed-rehearsal.ts` has a fallback that intentionally reads the **frozen Backup** when Source HEAD has advanced, to derive the snapshot's authenticated file inventory/salt for parity with new-key Destination. The fallback used `verifyGitHubReencryptionForkSourceWithTranscodeInventory()` with `expectedRepoId` still identifying the original Source, but `expectedBranch` identifying Backup. The trusted loader rejected this mismatched branch pair unless the caller provided `expectedPinnedCommitSha`. Unlike the correct frozen Backup content verifier, this inventory variant offered no pinned SHA/tree/repository identity arguments. The failure was caught by the fail-closed Recovery reader, misleadingly producing an unqualified `manual-recovery-required` even for an intact Backup.

## Narrow repair and negative proof

- `verifyGitHubReencryptionForkSourceWithTranscodeInventory()` now accepts the already existing `V4GitHubVerifiedSnapshotInput` contract rather than only `V4GitHubReencryptionSourceInput`; the shared verifier still pins the physical repository, specific branch ref and immutable commit/tree, checks embedded config Source repoId, authenticates every ciphertext blob and metadata record, and returns **no publication or Cutover authority**.
- Only the frozen Backup fallback in `inspectV4InstalledPreCutoverRecoveryAfterRestart()` now supplies `expectedPinnedCommitSha`, `expectedSourceTreeSha` and `expectedPhysicalRepositoryId` from the already-authenticated original snapshot. All ordinary Source validation callers remain unchanged.
- Extended the same regression to **change Backup to a different valid commit** (even with identical tree) after the positive read. The next inspection MUST return `manual-recovery-required`, `cutoverAuthorized:false` and `resumeSyncAuthorized:false`. This confirms the new branch allowance does not permit a mismatched immutable backup.
