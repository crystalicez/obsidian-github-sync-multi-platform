## Mandatory outcomes — exactly THREE roles in same physical GitHub repository

| Role | Example (illustrative only) | Contract |
| --- | --- | --- |
| Source / old branch | `main` | Exists already; retains OLD encryption and its Git history; continues independently accepting normal Sync from other devices indefinitely; never auto-deleted, locked or overwritten merely due to Re-encryption. |
| Frozen backup branch | `backup/rekey-2026-10-26` | NEW, distinct ref pinned to the exact authenticated immutable **source snapshot commit SHA**; preserves a recovery point even when source advances. Branch creation must be collision-safe; full readback and restoration proven before cutover. Can share existing Git objects, so is not a second full upload; SAME repository/shared failure domain, not an independent offsite copy. No automatic deletion. |
| Destination / new encrypted branch | `rekey/2026-10-26` | NEW, previously absent, distinct **orphan (zero-parent) Git branch**; contains all live logical data encrypted freshly with new passphrase, fresh KDF salt/material and new branch-scoped repo identity; NO shared source Git ancestry. It is NOT a regular branch clone or ciphertext-only copy. |

All three refs must be separate from each other and from disallowed default/destination names under the validated existing branch policy. Existing unrelated repository refs do not count as these roles. Do NOT add an in-place Re-encryption alternative or expose a choice to skip a backup branch. Backup is a distinct named Git branch; it may point at the source commit even though the source can subsequently move. The same physical repository choice and correlated deletion/credential risk were expressly accepted in D88; do not silently add a second provider/archive/password.

**Snapshot and concurrency:** Fork from one trusted pinned immutable source commit, with all file data consistent to that commit. Valid commits made to the source after the snapshot boundary do not invalidate the completed fork and do not flow to the destination. The source and destination become independent timelines; warn users clearly that changes do not propagate between them. Other devices may stay on the old branch forever or switch branch + passphrase **manually**. Do not auto-redirect them, block their ordinary old-branch Sync, force-push/force-pull, or auto-merge independent histories.

## Approved Settings entry and five-step Wizard

**Entry:** Settings → Encryption Settings → **Create encrypted branch** (Re-encryption). Use a separate Wizard rather than asking the user to edit GitHub branch, passphrase and PBKDF2 manually. Show a plain-English explanation: creates a re-encrypted copy on a new branch; keeps the old one unchanged; other devices may remain where they are.

1. **Preflight & Snapshot.** Display current GitHub owner/repo/branch as **read-only**, verified exact source commit SHA, remote encryption identity, eligible files/bytes. Check encryption/decryption access, existing Sync/recovery/conflicts, unsafe unsynced local edits, and snapshot consistency. Require user-directed resolution of pending local changes, no silent omission. Freeze/detect/revalidate *initiating-device local edits only* while preparing/cutting over; other machines are NOT paused.
2. **Destination & Encryption.** User enters a new branch name (suggest an editable collision-checked name, e.g. `rekey/YYYY-MM-DD`), and new passphrase twice. Show/hide controls; never log secrets. Provide PBKDF2 iterations (default **600,000**, permitted **600,000–1,200,000**) with concise performance guidance. Validate same physical GitHub repo, source/default/backup/destination distinctness, ref-name safety and **exact destination absence** with collision-safe create-time verification. The old branch remains read-only as a Wizard source even though other devices may keep syncing it.
3. **Review & Confirm.** Explicit summary of the **THREE branch roles**, pinned source SHA, backup ref, destination orphan ref, file/byte counts and selected KDF parameters. Highlight: *source remains active; other devices are not forced to follow; independent branch histories will diverge*. Warn that old ciphertext/old key exposure can persist in source, frozen backup and Git objects; this does NOT erase old Git history. Show shared-GitHub-repository backup loss risk and require an intentional confirmation before creation.
4. **Run, Progress & Verification.** Dedicated Re-encryption progress experience, separate from ordinary Sync, with per-phase file/byte progress and meaningful phases **Download, Decrypt, Encrypt, Upload, GitHub API, Integrity verification, Backup snapshot/readback/restore verification**. Show rates, elapsed time, concise diagnostics and expandable advanced details (source/destination SHA, PBKDF2, GitHub API latency, hashing/encryption time, peak memory, recoverable errors/recovery journal). No misleading "100%" or Success before comprehensive authenticated post-publication verification. On cancellation/crash/network ambiguity, fail closed and offer safe resume/recovery/revalidation where proven; never delete the source or switch settings on partial completion.
5. **Finish & Switch.** After complete backup/destination integrity/restore and durability prerequisites, switch **only the initiating device** to the new branch and encryption settings via crash-safe cutover; preserve its local data and use ordinary conflict safety (no implicit Force Pull/Push). Show all three final branch names, verified completion, and copyable destination settings guidance for any other device that **optionally** wants to follow. Leave source + backup untouched indefinitely unless the user explicitly chooses deletion in a separate deliberate operation.

**UX details accepted:** progressive disclosure rather than crowded advanced fields, accessible and unambiguous errors, branch collision and stale/unsupported encryption checks before high-risk actions, no impersonation of Sync progress, distinct clear labels Source/Backup/Destination, cancel/recover, optional detailed metrics; provide clear passphrase-loss and shared-repository failure-domain notices. Normal branch/encryption settings remain for ordinary connection configuration; altering the existing PBKDF2 setting alone does NOT re-encrypt an existing repository.
