# D164 — Best-effort WAL checkpoint and Re-encryption risk disclosure

Date: 2026-10-30. Owner decision: allow best-effort Re-encryption on systems where Node directory `fsync` is unsupported, with an explicit warning and Manual Recovery when needed. Physical power-off testing is not required. Do not claim a physical power-loss guarantee.

## Scope delivered

The desktop Node WAL storage now offers a **separate**, explicitly named `assertBestEffortCheckpoint(): Promise<"best-effort-readback-only">` operation. It does not modify `assertCrashDurable()` or forge its directory `fsync` evidence. The readback operation requires a live exclusive cooperative lock; no currently active writer; an allowlisted directory containing at least one WAL slot; safe non-hardlinked, non-symlinked, size-bounded slot files; matching consecutive descriptor-bound reads of each existing slot; and a final lease and writer check. Unexpected temporary files fail with `V4DesktopRekeyWalRecoveryRequiredError`. An unset or released lease also fails.

This readback establishes **only** that the current process can read a stable copy of the WAL slots at the check instant. It does not authenticate ciphertext, rule out ABA or an external uncooperative writer, guarantee a directory entry survives a power cut, or commit changes across Settings, SecretStorage and local Index. The caller must still use `createV4ReencryptionRecoveryJournal().assertHealthySnapshot()` with the correct journal key and immutable run identity. A corrupt but stable slot can pass low-level readback and fail journal authentication: a regression test deliberately demonstrates this separation. No result grants publication, Cutover, automatic Sync or old-key cleanup authority.

The existing Preview-only Wizard now displays a persistent best-effort warning before any potential confirmation. It explains that sudden power loss may lose acknowledged WAL/Settings/SecretStorage writes, warns the user to preserve both passphrases, Source and Backup, and states that uncertain restart state requires Manual Recovery rather than automatic Sync. Review/Run/Finish language no longer promises physical crash safety or says Windows directory `fsync` qualification is the only remaining blocker. The one-confirmation product intent is retained; no second confirmation, live Run button or secret deletion is introduced.

`V4_OWNER_REENCRYPTION_DECISIONS` records `unsupportedDirectorySyncPolicy: "best-effort-with-explicit-warning-and-manual-recovery"`, `bestEffortWalReadbackRequired: true`, and `uncertainRestartRequiresManualRecovery: true`, alongside the earlier no-physical-proof and no-unverified-Cutover policy.

## Validation and remaining work

Focused real-Windows disposable WAL tests include a successful AES-GCM journal readback, empty-WAL rejection, stable-but-corrupted ciphertext requiring journal authentication, foreign temporary-file refusal, and released-lease refusal. Existing strict directory-fsync refusal and write-race regressions remain. Wizard tests assert user-visible warnings, single-confirmation intent, and continued Preview-only no-write behavior.

**Still not an operational migration:** The publication coordinator and protected Git ref writers still call the strict `assertCrashDurable` contract. The best-effort readback API is not yet wired as a replacement for those calls, nor is a fully checked Cutover/reconciliation protocol implemented for Settings, SecretStorage, Source/Shadow Index and branch selection. Implementing the final user-confirmed best-effort path must require authenticated WAL generations, exact remote ref/backup evidence, safe replay rules, old-key retention and fail-closed Manual Recovery before changing any local selector. The first-release gate remains `blocked`; the Wizard stays Preview-only. Do not silently bypass all `assertCrashDurable` call sites, weaken ordinary Sync, add a Native Helper, or use GitHub Actions.
