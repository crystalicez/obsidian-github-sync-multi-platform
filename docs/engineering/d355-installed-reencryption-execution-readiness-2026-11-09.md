The implementation specifically warns it is **not wired to Wizard Run** until recovery-safe runtime index routing is established. Individual primitives do not make the cross-surface transaction complete.
- `src/lib/v4/reencryption-mobile-initiator-reader.ts` uses `DataAdapter.readBinary(path)` (whole-file allocation) and **refuses a single included file greater than 32 MiB**. Historical **48 MiB parts remain readable**. The Mobile ceiling must not be lifted without proving a bounded-read capability and memory safety. Desktop has a distinct bounded physical read implementation.
- `docs/release-gates/reencryption-wizard.json` remains `status:blocked`; only topology approval is passed. None of six remaining checks is automatically promoted by this analysis or by a green offline suite.

## Product-scope decision resolved: A approved on 2026-11-09

The currently implemented Mobile initiator cannot verify an individual included file over **32 MiB** without unbounded `readBinary`. Separately, new GitHub writes cap each ciphertext object at **8 MiB** and budget **400 content mutations per revision**, so a single 5 GiB file cannot be safely published under the current writer policy even on Desktop; the old 48 MiB parts are **read-compatible**, not newly writable. The owner chose capability-gated Mobile initiation (A). D364 now compares the physical Mobile Vault inventory to per-file sizes/paths authenticated from a single immutable Source Git commit in the read-only Wizard Preview; a remote-only oversized file or local-vs-Source mismatch blocks Preview. The Runtime independently checks the current physical inventory before arming its one-way Sync fence. **Neither metadata comparison nor Preview authorizes actual execution; the installed migration transaction must additionally require the authenticated Source record set and double-pass, lease-held physical parity at the point of publication.** This is a scope decision, not proof that ordinary Mobile Sync can handle a large file. D363 separately exercises the normal Sync content-source path with a 32 MiB + 1 byte logical file: Mobile reports no bounded read, rejects before `readBinary()`, and still lacks bounded stage commit. Actual Android/iOS acceptance remains pending. The two options were:

- **Approved A, capability-gated initial release:** Mobile may initiate only when every included file is at most 32 MiB. For larger files, Desktop initiation plus manual Mobile reconfiguration could be offered **only after the ordinary Mobile Sync/download paths for those file sizes are separately accepted**. Reject unsupported Mobile initiation during read-only preflight, **before** arming a one-way Sync fence; do not pause ordinary existing Sync merely because Preview discovers an unsupported file. This preserves memory safety but is **not complete initiating-platform parity**.
- **Not selected, possible future B:** Require a proven bounded mobile file-read route for files over 32 MiB and physical Android/iOS acceptance before enabling Re-encryption. This increases scope but avoids promising identical capabilities the API cannot provide.

Keep A in force and do not relax the mobile memory ceiling or claim large-file Mobile Sync support without separate bounded-I/O engineering and physical-device proof. Existing user decisions still govern: common best-effort UX, one confirmation before migration, initiating-device automatic switch only after verified safe completion, Manual Recovery on ambiguity, independent old Source + frozen Backup + new orphan Destination in one repository, no automatic branch deletion, no GitHub Actions, no Native Helper by default.
