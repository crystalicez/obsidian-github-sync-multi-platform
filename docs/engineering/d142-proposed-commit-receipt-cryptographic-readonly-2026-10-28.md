# D142 — Proposed authenticated local commit marker: read-only, uncommitted, non-authorizing

Date: 2026-10-28. The Re-encryption Wizard is still **Preview-only**. Release gate stays **blocked**.

## What was implemented

`src/lib/v4/reencryption-proposed-commit-receipt.ts` provides an **isolated proposal**, not a production-writable commit:

- `V4ReencryptionProposedCommitIdentity` pins the exact run ID, WAL generation, source/shadow Index root, device ID, all three distinct same-repository Source/Backup/Destination refs, Source Git commit/tree, Destination Git commit/tree, full candidate manifest SHA-256 and the two distinct SecretStorage ID strings.
- `sealV4ReencryptionProposedCommitTestVector()` produces a test-only **AES-GCM** encrypted marker in memory and **never persists it**. The marker uses V4's existing encryption primitive with `journal` payload kind, distinct domain-separated AAD binding run/Source/Destination, and a separately derived AES key (HMAC-SHA256 from an independently supplied V4 journal key). Nonces are generated by the existing crypto primitive. The plaintext schema phase explicitly says **`hypothetical-commit-marker-uncommitted`** — not `committed`. Serialized identities require exactly the 14 recognized fields; extras, aliases, malformed refs and unsafe relative roots reject. No passphrase, plaintext note, token or key bytes appear in the marker data or returned report.
- `inspectV4ReencryptionProposedCommitAfterRestart()` is a **read-only** testable inspector. The caller supplies an actual local adapter, independently pinned expected identities, key, installed Settings snapshot, authenticated two-slot WAL reader, SecretStorage presence reader, and external exclusive lease/durability assertions. It validates the marker's canonical Base64, max 8-KiB byte budget and AEAD tag + exact decrypted canonical record. Under one caller-held lease, it brackets **two** readbacks of the actual selected Destination Index, separate complete Shadow Index, marker bytes, observed WAL contents and selected Settings/SecretStorage values. It requires the WAL's verified Backup Source commit/tree, Destination commit/tree/manifest and prepared candidate receipt to match. Adapter `read/exists/stat`, WAL reader, callbacks, identity/settings snapshot and journal key bytes are pinned across awaits. A holder that skips the inspection body cannot forge a positive report.
- A fully matching observation is named **`authenticated-marker-with-destination-observed-uncommitted`** and **ALWAYS** hardcodes `localCutoverAuthorized:false`, `resumeSyncAuthorized:false`, `rollbackAuthorized:false`, `remoteWritesAuthorized:false`, `oldPassphraseCleanupAuthorized:false`. All inconsistencies report `manual-recovery-required`; lease, durability and authenticated-WAL read errors propagate without authorization. No adapter write, Settings mutation, SecretStorage set/clear, Vault edit or GitHub write occurs.

The key is supplied by a caller; authenticated means **valid under that supplied key** only. It does not certify authentic *origin* when a local attacker controls the key or storage. It is a hypothetical *marker* rather than a durable receipt; the bytes may be lost after acknowledged write, copied from another replayable state or remain after an incomplete cutover. The test-only encoder must **not** be wired to the Re-encryption Wizard.

## Negative tests and limitations

`tests/v4/reencryption-proposed-commit-receipt.test.ts` (focused **10/10**) uses production AES-GCM operations and an in-memory adapter. It tests successful authenticated readback remaining nonauthorizing, Source/destination selector conflict, torn/malformed/oversize marker, wrong key, wrong run/source/destination SHA and WAL manifest, a same-key forged extra `cutoverAuthorized:true` field or forbidden `committed` phase, wrong Backup role, missing old/new secrets, missing Shadow, Settings/Index/marker/WAL/key changes during awaited reads, injected adapter method replacement, malicious skipped/double-invoked lease holder, lease/durability/WAL exceptions and strict schema/branch/SecretStorage validation.

`tests/recovery/reencryption-proposed-commit-receipt-windows.test.ts` (Windows real file **1/1**) writes **only disposable test files** inside `.tmp`: active/Shadow indices, test-vector marker and a settings.json surrogate. It then constructs a **new read-only** adapter and reopens those files for verification, including missing old SecretStorage and torn marker cases. Its WAL, lease and durability are in-memory stubs. This is **not** a real Obsidian `saveData()` durability test, physical reboot/power-loss test, real SecretStorage disk readback, live GitHub three-ref readback, or installed two-device Obsidian acceptance.

The D142 inspector **does not** invoke D138's complete GitHub blob/decrypt-and-remote verification, does not validate live Backup ref at the commit boundary, does not trust the original Source Index root to survive overwrite, does not fence non-cooperating external Vault writers and does not inspect OS physical fsync or the persistence of Settings/SecretStorage. A plausible positive marker and exact local WAL snapshot remain only **point-in-time information**. D142 does not add a new journal phase or a durable `committed` receipt. Never promote a D142 result to cutover authority without independent platform-backed transaction semantics.

## Next prerequisites

The system still needs a fully specified idempotent crash-recovery protocol whose single authoritative commit selector is demonstrably power-loss durable and can reconcile Obsidian Settings, independent local Index and SecretStorage on **each supported platform**. Windows Node-only directory `fsync` is unsupported in this environment; other desktop/mobile physical qualification is absent. Before implementing a real writer, owner approval is needed for any Native Helper or fundamental selector/storage architecture choice. The existing policy forbids treating simple `saveData()` acknowledgment/readback as physical durability. Preserve old accessible SecretStorage value until independent durable verified completion, and retain Source/Backup/Destination refs under the owner-approved topology.
