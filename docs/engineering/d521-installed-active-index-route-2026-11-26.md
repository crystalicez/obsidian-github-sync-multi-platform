# D521 — Authenticated installed Destination Index activation

Starting from native-qualified D520 a4c5b38. New internal activation entry point requires explicit acknowledgement, exact discovered locator digest, hydrated Destination key, current Destination Settings, complete frozen Backup/Destination/WAL/secret/Index proof and fresh physical Vault parity plus pinned Source ref under the same owner-held native WAL lease. Source and Shadow are not copied, moved, or overwritten by activation.

The new Destination-key AES-GCM selector is written at the D145 separate selector path first. It binds run, historical Source and Destination, physical repository/device, secret IDs, exact Settings/intent/fence digests, original Source Index digest and initial Shadow digest/stable baseline. After fresh proof and readback, an identical fixed active-route record is written last. Only the complete matching authenticated pair permits narrow ordinary Sync routing, not a generic authorization flag. Selector-only with an exact authenticated match may be resumed after fresh proof. A torn/foreign selector or marker is not blindly overwritten. A complete pair can be observed after a lost acknowledgement. All original fence/intent artifacts and both keys remain intact. This is best effort, not a physical power-loss guarantee.

Each ordinary Sync attempt independently authenticates the current Git repository/config, live owner/secret custody, exact persisted Settings, both route records, historical fence/intent, original Source Index and selected Shadow identity. The selected Shadow is loaded and saved; the route is checked again before Index save. Initial remote records are bound while the initial commit remains selected, allowing mutable local mtime/dirty bookkeeping. Later cache evolution uses normal V4 Index/WAL checks. History file-ID lookup also selects the authenticated route. Missing/tampered route fails closed with fence retained. No speculative empty remote initialization on the active route. Force and Settings writes remain blocked; no UI Execute wiring, old-key deletion, new migration or release. A corrupt/missing active Shadow cache currently needs Manual Recovery rather than automatic rebuild; settings remain exact-bound, including unrelated preferences. Future work must safely address these restrictions and active recovery diagnostics before opening public Execute.
