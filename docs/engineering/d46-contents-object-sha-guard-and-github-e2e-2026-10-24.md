## D46 deterministic Contents identity safety gap

`GitHubClient.getFileBytes` previously treated a Contents HTTP 200 decoded base64 body as verified when the response's `sha` was absent or did not match the canonical lowercase 40-character Git object ID shape. The code set `verified = true` and skipped SHA-1 matching entirely for malformed identities. A malformed Contents response could therefore be accepted without establishing that the bytes match an identified Git blob. This is a demonstrated response-validation gap, **not a proven cause of D38's intermittent Missing V4 remote object or D45's different branch-ref 404**.

RED → GREEN: new `tests/v4/github-contents-sha-guard.test.ts` failed against previous code for omitted/empty/malformed/uppercase SHA while preserving a valid Git blob SHA read. D46 requires exact 40-digit lowercase hex `sha` on every Contents 200 before returning content or falling back to the blob endpoint; accepted inline content must match the Git blob SHA-1. Existing fake transport/Contents test fixtures were updated to valid SHA formats, including calculated real SHA-1s for one-byte and short textual blobs. It does not change HTTP requests on valid inline GitHub responses, Git ref logic, GitHub writes, encryption, hashes stored in V4 metadata, recovery or Sync conflict/delete semantics. Malformed API responses now fail instead of being treated as trusted data.
