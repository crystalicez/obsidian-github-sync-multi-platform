# D83 — Complete immutable orphan destination Git commit audit (read-only)

Date: 2026-10-26 (Asia/Bangkok). Based on clean/pushed D82 `356ddaec86226ed8fa3e9b580672828cc8600b54`. Isolated worktree `.worktrees/d83-exact-commit-destination`, branch `audit/2026-10-26-d83-exact-commit-destination`.

## Gap closed at a bounded read-only evidence layer

D82 verified individual staged Git blobs retrieved by Git SHA, but blobs can exist without a reachable Git tree/ref and without an authenticated V4 HEAD/index. D83 adds `verifyV4ReencryptionDestinationExactCommit` in `src/lib/v4/reencryption-destination-exact-commit.ts`: an **independent read-only** complete destination proof scoped to a single explicit immutable orphan commit SHA and D79’s finalized destination manifest/receipts. No source-vault changes, ref creation, API mutation, WAL promotion, passphrase setting changes, publication or cutover.

The caller supplies a D74 approved same-repository orphan plan, an **independently authenticated** pinned source tree SHA/config, expected exact new root SHA, expected finalized encrypted destination config, the D79 candidate logical records and ciphertext receipts, destination passphrase, and a trusted GitHubClient scoped to the **approved physical repository**. This does not establish where the caller obtained the expected D79 receipt list, and does not constitute user-backup verification.

## Verification order and fail-closed properties

1. Validate plan/sha/source/destination branch coordinates. Check GitHub repository numeric ID and full name plus the **exact destination branch ref** against the requested root SHA.
2. Read the immutable Git commit by full SHA; require its returned SHA to match the request; reuse D74 root topology proof: **zero parents**, new tree distinct from original source tree, source/destination encrypted config identity, fresh PBKDF2 salt, new KDF policy.
3. Read the pinned commit tree with `recursive=true`; require exact returned tree SHA, `truncated:false`, <=100,000 entries, supported normalized paths, unique blob paths, regular `100644` file modes. A symlink, gitlink, duplicate blob, incomplete tree, SHA mismatch or unsupported entry fails closed. This is bounded but a very large Git tree must be audited by a paged nonrecursive visitor in a later stage.
4. Read config and encrypted HEAD/index shards **only by their paths in that exact commit tree**; verify each returned blob byte sequence has the complete Git blob SHA-1 declared in the tree. Derive destination V4 keyring with PBKDF2 and decrypt/AES-GCM-authenticate HEAD + shards using the existing production codecs and AAD.
5. Reuse D68 `inspectV4ReencryptionInventory` to enforce every shard bucket, logical signature, keyed path HMAC, opaque storage path and collision rules. Compare **every committed logical file record** with the D79 finalized candidate record, including logical path, path ID, file ID, SHA-256, size, mtime, remote version, storage, path/pack identifiers. The freshly migrated orphan must have **no tombstone/dirty records**; old history and tombstones remain on the retained original branch.
6. Require **exactly one set** of expected ciphertext receipt paths with Git SHA and <=8 MiB byte lengths, matching every remote object path referenced by the authenticated index. Require the **entire root Git tree blob-path set** to equal `config + head + every index shard + expected ciphertext objects`, rejecting missing or surprising blob entries. This is stricter than D82's blob-by-SHA check.
7. Independently fetch each reachable encrypted blob by its *tree SHA*, re-check full Git blob SHA and receipt byte length, and use production `V4StorageCodec.readToSink` to **AES-GCM-decrypt and hash each file** without writing it to an Obsidian vault. Packed/chunked records and empty files follow the original decoder. Verify every plaintext SHA-256 and byte size and BigInt whole-vault totals. The output contains no plaintext paths and keys/salt are zeroed on success or exception.
8. Re-check destination branch ref SHA and physical repository identity after all reads. Fail if the branch moved during audit. ABA, concurrent old-branch writes and cross-device cutover are **separate unresolved safety policies**.

The returned frozen report says `integrityScope:"exact-orphan-commit-all-live-content"` with exact commit SHA and authenticated counts. It **always** has `backupVerified:false`, `secondDeviceRestored:false`, `permissionToPublish:false`, `cutoverAuthorized:false`. In particular, this audit is **post-commit** and cannot itself authorize the earlier creation of a commit or ref.

## Important limits and next stages

D83 does not re-encrypt a **real** user's vault into a branch, verify source quiescence across other devices, persist D79/D81 WAL into an fsync-durable native or mobile backend, reconcile ambiguous WAL receipts safely, verify an independent recoverable backup, or restore into a **second actual installed Obsidian instance**. Synthetic second GitHub API reader is not proof of physical second-device acceptance. A root commit/tree may be valid while a user's backup is absent, and source-branch history remains reachable in the same repository. Future helpers must never treat this report as permission for cutover or as proof a post-publication old client cannot write.

D66 first-release `docs/release-gates/reencryption-wizard.json` remains `status:blocked` with only `ownerApprovedMigrationTopology:passed`; six acceptance conditions still pending. Owner approved new orphan branch within same physical repo plus old source retained for recovery and independent second-device testing, but **has not approved old-branch Sync freeze vs continued reconciliation**. Do not choose that high-risk policy without explicit owner instruction.

**Next safe work:** verified independent backup/readback contract; platform WAL power-loss durability + cross-process lease; a bounded orchestrator that binds staged output and post-commit readback without publishing or cutover automatically. Multi-device old-branch safety and actual installed Obsidian acceptance remain gated.
