# Scalable conflict review: compact whole-hunk decisions — 2026-10-18

## Safety/performance bug and bounded correction

**Observed:** The paged native Obsidian conflict UI displayed at most **48 lines per side**, yet clicking a whole-hunk shortcut (`Keep all local lines`, `Keep all remote lines`, `Keep both sides`, `Omit both sides`) created an individual string-keyed decision in a JavaScript `Map` for **every local and remote line** in that hunk. A single large hunk with hundreds of thousands of lines could therefore cause unnecessary synchronous CPU work, unbounded per-line metadata allocation and UI unresponsiveness. The risk is specific to shortcut decisions; line-by-line review must remain possible and all previously reviewed choices must be honored.

**RED→GREEN:** Added a behavioral test with **100,000 changed lines on each side**. It was RED before implementing optional whole-hunk defaults in `mergeV4ReviewedLines` and is GREEN after. One `Map<number,V4ReviewChoice>` entry represents a default for each hunk, and only individually overridden lines get `Map<string,V4ReviewLineDecision>` entries. Exact merge reconstruction still honors both the default and exceptions. No implicit choices are added to unreviewed hunks.

**Native UI:** `V4PluginRuntime.askConflict` now stores a constant-size decision per whole-hunk shortcut. Previously reviewed per-line overrides within that hunk are removed when another whole-hunk shortcut is chosen, exactly as they were overwritten before. Individually clicking **Keep / Omit** after a shortcut creates only the requested exception. `reviewedLineCount` and each hunk's partial-decision count maintain the **all changed lines explicitly decided** prerequisite, with correct cross-page progress and `aria-pressed` state. Manual merged-text edits and Reset remain unchanged.
