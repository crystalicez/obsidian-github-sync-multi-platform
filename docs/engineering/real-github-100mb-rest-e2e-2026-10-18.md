# Windows 100 MB encrypted GitHub REST V4 E2E — 2026-10-18

## Scope and trust boundary

The maintainer's permanent active test-file limit is **100 MB = 100,000,000 bytes**. This qualification uses an actual 100 MB file and two isolated disk-backed Windows vault adapters with the production V4 sync session, encrypted objects, bounded content reads, and verified staged commit. The GitHub portion invokes the **real GitHub REST API** on a pinned disposable private repository and an absent `obsidian-sync-e2e/local-...` branch. The test fixture does **not** run inside the Obsidian Electron desktop application. These distinctions matter for release acceptance.

Only `tests/v4/github-transport.test.ts` was pre-existing user WIP in the primary audit workspace; it was never staged or modified by this work.

## RED: initial GitHub API limit surfaced by a real test

With the prior 48 MiB V4 chunked writer default, the real encrypted 100 MB Force Push failed on `POST /git/blobs`: **HTTP 422** with GitHub indicating the blob input was too large. The public REST Git blobs documentation lists HTTP 422 as validation failure but does not specify a reliable *Create a blob* request size threshold. Do **not** confuse GitHub's 100 MB single-object repository limit with a guarantee that a 48 MiB base64 JSON API request succeeds.

The initial failed run confirmed that the disposable branch was absent at cleanup. No default-branch write, merge, or release occurred.

## GREEN: real GitHub 100 MB encrypted sync and recovery

With the E2E-only resource budget restricting new object parts to **8 MiB**, the same target passed the full scenario. That established the empirical cap. Then production `selectV4WriterPartBytes` was changed to cap **new chunked GitHub REST blob parts at 8 MiB**, while `V4_PART_BYTES=48 MiB` remains unchanged for historical reader/descriptor compatibility. The E2E-only resource override was removed, and the live test **passed again with the production writer default**:

- Credentialed read-only preflight confirmed pinned repository numeric ID `1284153873`, readable default Git ref, and an initially absent disposable branch `obsidian-sync-e2e/local-100mb-20261018-932df8e`.
- Real **encrypted Force Push** of an actual 100,000,000-byte Windows file through production V4 session and GitHub REST returned `force-push`.
- **No-op sync** preserved the published commit SHA and did not create a new revision.
- A controlled **bounded-stage append failure** during Force Pull left no partial final target.
- Force Pull retry completed with exactly 100,000,000 bytes and SHA-256 identical to the local source: `f079cad53add0091ed5d0409b0469f9f5cb745b8c280be685dda73203dea90e8`.
- Production-default live verification: test **1/1, exit 0**, reported scenario elapsed `103278 ms`, 3 source bounded reads, 13 receiver staged writes (across failed and successful attempts), one committed stage.
- The E2E teardown **confirmed deletion/absence of the disposable branch** after each completed run. Unreachable Git blobs created during the test may remain until GitHub's garbage collection; branch cleanup is not a guarantee of object-store garbage collection.

Locally, `pnpm test:soak` uses 100 MB generated bytes and the new disk-backed encrypted V4/Git simulator scenario. That test independently passed encryption, no-op, a bounded append interruption and retry with matching SHA-256.

## Subsequent medium-file writer threshold update (same date)

The historical item below stating that 8–50 MiB writes still use the 50 MiB single-blob threshold is **superseded** by the subsequent maintainer-approved change recorded in `docs/engineering/v4-rest-safe-medium-writer-2026-10-18.md`. New files larger than 8 MiB now use parts up to 8 MiB, while legacy 50 MiB single blobs and 48 MiB parts remain decodable. Local real-file encrypted 16/32/50 MB round trips pass, but a new **16 MB live GitHub Force Pull pass has not been obtained**. The 100 MB GitHub success documented above predates that medium threshold change and should not be presented as an exact new-code-SHA receipt.

## Release qualification limitations

1. These live runs used the current audit working tree before freezing a new full commit SHA; they do not substitute for a clean exact-SHA release receipt or hosted CI.
2. The test used Node-backed synthetic vault adapters on Windows, **not the native Obsidian Desktop UI/process**. The baseline's native physical Windows acceptance remains separate, including peak process working set and user-facing interruption/restart observations.
3. The tested new 8 MiB cap applies to the **chunked writer path** (the 100 MB scenario). Single objects and packs at smaller logical sizes still follow the pre-existing 50 MiB chunk threshold / pack planner. A separate compatibility design and empirical REST limit review is required before changing those thresholds because old V4 clients may reject newly chunked files below 50 MiB. This is a **known open risk**, not a claim that all 1–100 MB workloads are now certified.
4. GitHub API responses can change and rate-limit. The 8 MiB cap is an empirically verified conservative setting, not a published permanent GitHub guarantee.
5. No main/master merge, stable release, mobile device certification, or Hosted Actions CI qualification was performed.

## Repeatable commands and safety

Use only a disposable repo with a preconfigured restricted `.env.github-e2e` token. Never log tokens. Both tools **fail closed** without an explicit pinned target ID or a fresh `obsidian-sync-e2e/local-...` branch.

```powershell
node scripts/preflight-windows-100mb-github.mjs --expected-repo-id=<PINNED_TEST_REPO_ID> --branch=obsidian-sync-e2e/local-<UNIQUE_TEST_RUN_ID>
node scripts/run-windows-100mb-github.mjs --expected-repo-id=<PINNED_TEST_REPO_ID> --branch=obsidian-sync-e2e/local-<UNIQUE_TEST_RUN_ID>
```

Never point this at source repo, default branch or real notes. The runner and the live scenario independently recheck that the branch is absent before writing. The live test no longer resets or deletes an unexpectedly occupied branch on startup; it only enables its teardown after confirming the branch was initially absent. On a failed/crashed process where teardown cannot verify branch absence, **do not re-run destructively** until the exact disposable branch is inspected and cleanup is explicitly reconciled.
