# V4 Performance and Resource Qualification Methodology

Originally drafted 2026-07-30; permanent maximum test size set by maintainer on 2026-10-18.

**All current and future generated-file, virtual-stream, soak, and physical large-file test workloads must be no larger than 100 MB (100,000,000 decimal bytes).** The 100 MB cap concerns tests and acceptance claims, not the production format, transport implementation, or GitHub's repository guidance.

**Current V4 write rule:** newly uploaded files above **8 MiB** are split into REST-safe parts no larger than 8 MiB. The historical 50 MiB single-blob and 48 MiB part reader compatibility remains unchanged. Medium 16/32/50 MB encrypted file-backed round-trips and 100 MB encrypted staged round-trips are required regression coverage.

## Required workloads

1. Unchanged 10k-file metadata scan and one changed-file scan.
2. 1,000 small changes and each conflict policy/action path.
3. Bounded pack batch and threshold-1 / threshold / threshold+1 content sources.
4. Writer-boundary planning (8 MiB, 16 MB, 32 MB, 50 MB, 100 MB), encrypted medium 16/32/50 MB disk-backed round trips, old 32 MB encrypted single-blob decode, chunked upload/download, and incremental 100 MB cryptographic soak.
5. Real Windows local 100 MB generated-file SHA-256 and bounded filesystem copy.
6. Physical Obsidian encrypted Force Push → no-op → separate clean-vault Force Pull → SHA-256 equality, including controlled recovery on an explicitly verified disposable GitHub target.
7. Android/mobile smoke only where its bounded I/O capability is independently supported. No claim of Android 100 MB support without evidence.

## Commands (maximum 100 MB)

```bash
pnpm test:fast
pnpm test:repeat
pnpm test:recovery
pnpm test:resource
pnpm test:feasibility
pnpm test:soak
pnpm test:windows:100mb
```

`pnpm test:soak` defaults to exactly 100,000,000 generated bytes; `--bytes` rejects any value larger than 100,000,000. The underlying soak test also rejects oversized direct `V4_SOAK_BYTES` configuration instead of silently truncating it. `pnpm test:windows:100mb` writes the actual file and a staged filesystem copy in a new ignored `.tmp/windows-100mb-*` directory, verifies exact sizes and SHA-256 and records a JSON report. **This local I/O test does not execute Obsidian or GitHub sync.**

Only a fully authenticated, pinned, disposable GitHub target may be used for a live encrypted 100 MB round trip. The opt-in `scripts/run-windows-100mb-github.mjs` exercises real encrypted V4 REST Force Push, no-op, staged failure/retry and SHA-256 on two real Windows disk files and verifies branch cleanup. The runner requires explicit `--expected-repo-id` and `--branch=obsidian-sync-e2e/local-...` arguments and refuses existing branches. This is a Node V4 harness, not an Obsidian Desktop application session. A read-only preflight alone is not a sync result. Never execute live writes against the source repo, real notes or a default branch. See `docs/engineering/real-github-100mb-rest-e2e-2026-10-18.md`.

## Measurements

Record elapsed time, logical byte count, selected part size and count, peak RSS / private working set (with measurement method), request and mutation counts, retries, pacing, staging-space usage, restart behavior and final SHA-256 equality. Do not mix Node RSS with browser JS heap or Windows working set.

## Evidence rules

`tests/baselines/v4/windows.json` and `android.json` are evidence, not targets. Use `null` for unmeasured values and `pending` when a required physical case has not run. A passing 100 MB virtual stream or filesystem copy must not be recorded as an encrypted Obsidian/GitHub Force Push/Force Pull pass. Update the source commit and environment with the actual run.

Older larger-size experiments remain retrievable through Git history for traceability, but **no oversized workload is part of active test instructions**. Do not restore the old commands, increase fixture sizes, or infer support for untested physical file sizes.
